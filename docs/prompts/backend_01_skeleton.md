# Backend task 01 — runnable root skeleton and shared contract

Apply `docs/prompts/00_master.md` first, including the first-task `CASE DELTA`. This prompt is for the strongest developer, the Backend / AI lead. Work on `lane/backend`, except for the explicitly requested first-baseline publication to `main`.

## Scope and first handoff

Create one Next.js App Router + TypeScript app at the repository root. Do not scaffold a nested app or overwrite existing documentation/data. Own `src/app/api/**`, `backend/**`, `src/shared/**`, `package.json`, root config and lockfile. The bootstrap exception permits only the minimal Next.js page/layout/styles in frontend paths before frontend starts. Do not build product screens.

Prioritize a runnable baseline and shared contract, commit it under your own identity and publish it to `main` first so other members can pull at T=0–10. Use a normal coordinated merge/push if branch rules require it; never force-push or bypass protection. Report a blocked publication explicitly. After that handoff, continue on `lane/backend`; coordinate later contract changes with frontend and QA.

## Deliverables

1. Install/configure Next.js, TypeScript, Zod, OpenAI SDK, mammoth, pdfjs-dist, xlsx, Vitest and tsx. Confirm actual input formats with QA at T=0. Provide working `dev`, `build`, `typecheck`, `lint` and `test` scripts using the installed tool versions; do not assume obsolete framework commands. Use Node runtime for parsing/API routes.
2. Set `.gitignore` to cover `.env*`, with `!.env.example`, plus `.data/`, `.cache/`, `node_modules/`, `.next/`. Write `.env.example` with placeholder entries `OPENAI_API_KEY` and `OPENAI_MODEL`; no real values. Never read or print `.env.local` or keys. Record a non-secret embedding model selection in configuration and coordinate it with QA.
3. Implement `src/shared/contract.ts` with all Zod schemas and inferred types from PLAN: `Evidence`, `DocumentInfo`, `Unit`, `UnitChange`, `OrgFunction`, `FunctionLineage`, `Finding`, `Summary`, `Conclusion`, `AnalysisResult`, `AnalysisJob`, review input and supporting enums/objects. Preserve exact camelCase names and enum spelling. Export shared types for consumers. Validate reference integrity and cardinalities at the appropriate server boundary, beyond shape validation.
4. Create `src/shared/analysis-result.example.json`, schema-valid with `isMock=true`. Use coherent synthetic Russian units, functions, citations and finding IDs, valid cross-references, accurate summary counts and all six conclusion section keys. Do not present synthetic source quotations as organizer data. Unverified diagnostics cannot support conclusion claims.
5. Implement DOCX/PDF/XLSX ingest under `backend/**`. Output internal fragments with stable ID, document identity, side, original text and locator. Preserve clause numbers such as `3.2.1` or `п. 5`, headings and table context; PDF pages and sheet rows are one-based. Put sheet name and row in `locator.label`; do not invent DOCX pages. Warn instead of crashing on PDFs without a text layer. Apply PLAN's upload and parser failure behavior, preserving readable coverage and identifying omissions.
6. Implement `backend/llm.ts`: OpenAI client from runtime env; structured chat and embedding helpers; disk cache by stable input hash including operation/model/prompt/schema versions; bounded retries inside try/catch; sanitized failures. No actual secret is read by your tools or included in logs/cache keys. All calls, including embeddings, use cache. Export `validateQuote` with whitespace, case and quote-character normalization, preserving original source text; empty, fabricated or paraphrased quotes fail.
7. Implement `backend/pipeline.ts` with exported `runAnalysis`. Agree its typed input with QA before evaluation integration; use parsed upload inputs with explicit sides rather than requiring QA to emulate HTTP. Stub semantic stages may return empty arrays but must emit actual stage transitions and state that they are stubs. Include all seven stage keys in order. A result produced with stub semantics must have `isMock=true` and a warning that it is not an audit. Do not run fake timers to simulate progress.
8. Implement an in-memory job store persisted to `.data/` using atomic writes. Persist stage transitions, completed results and review updates. Reload completed jobs on restart; mark interrupted running/queued jobs failed with a sanitized explanation. Validate stored payloads and prevent concurrent review writes from dropping updates.
9. Implement `POST /api/analyses`, `GET /api/analyses/:id` and `PATCH /api/analyses/:id/findings/:findingId/review` using the shared contract and PLAN's response/error decisions. POST accepts multipart `before[]` and `after[]`, validates both sides, and returns HTTP 202 `{ id }`. GET returns `AnalysisJob`. PATCH validates input, persists review and server timestamp, and returns updated `Finding`; unknown IDs are not silent success. Review does not modify source verification.
10. Add colocated Vitest tests under owned backend/shared paths: a real quotation passes, a fake one fails; include normalization and empty-input cases. Validate the shared example JSON against Zod and check its references/count semantics. API stubs must also have a smoke check for create, poll and review using the shared example as an explicit demo job if necessary; do not claim stub findings were detected.

## Boundaries and acceptance

This task prepares the skeleton, parsers, schema and plumbing. It does not implement frontend screens, QA's fixture generator or the full later matching/lineage/findings engine. Do not hide these omissions. After this task, the next backend slice must extract verified functions from one actual document by T=40; empty stub output does not satisfy that walking-skeleton milestone.

Coordinate with QA on the DOCX writer dependency, API-check/evaluation npm commands and the `runAnalysis` interface. QA cannot edit your package/config files. Shared example JSON is backend-owned; frontend maintains its richer mock separately against the same schema.

Run relevant Vitest tests, typecheck, lint and a build smoke check. Exercise the endpoints, including invalid input and a persisted review, without exposing credentials. Report commands and exit codes, changed files, blockers and requests for other lanes. State exactly which baseline reached `main`, which work remains on `lane/backend`, and which stages are stubs.
