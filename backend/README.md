# Backend OrgTrace AI

Серверный код расположен здесь, frontend — в `src/`, общая Zod-схема — в `src/shared/contract.ts`. Одно Next.js-приложение, корневой package и один origin. Отдельный сервер или установка зависимостей внутри `backend/` не нужны.

| Файл | Назначение |
| --- | --- |
| `handlers.ts`, `http.ts` | API и ограниченный разбор запросов |
| `ingest.ts` | TXT/DOCX/PDF/XLSX, исходные фрагменты |
| `clauses.ts` | Пункты, подпункты, TOC, exact/fuzzy alignment |
| `semantic.ts` | Опциональные embeddings и LLM, проверка цитат и ролей |
| `regulation.ts` | Структура положений БВА, функции, lineage, checks, findings и сводка |
| `pipeline.ts`, `stages.ts` | Десять реальных этапов и состояние |
| `store.ts`, `files.ts` | Атомарное хранение jobs/review, restart и несовместимость v0.1.0 |
| `llm.ts` | Cache, structured output и ограниченные повторы |
| `seed-demo.ts` | Отдельный явно синтетический пример |
| `*.test.ts` | Парсеры, основная пара, API, UI adapter, состояние, схемы и AI transport |

Запуск из корня: `npm ci`, `npm run dev`. Проверки: `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`. API и ограничения реализации: [CONTRACT.md](../docs/api/CONTRACT.md).

Вызовы AI включаются при runtime-конфигурации `OPENAI_API_KEY` и `OPENAI_MODEL`; `ORGTRACE_AI=false` отключает их для воспроизводимых локальных проверок. Без AI сравнение работает с явным предупреждением, возможные потери остаются диагностическими. Не читать/логировать `.env.local` и секреты. UI никогда не импортирует backend-модули.

QA использует `runAnalysis` из `backend/pipeline.ts`; основной набор — `data/samples/before/` и `data/samples/after/`. `.data/` и `.cache/` игнорируются Git. Реальные загрузки не являются mock; это не означает полный смысловой аудит или подтверждение всех кандидатов. Поддержка структуры других шаблонов, DOCX auto-numbering и экспертная разметка остаются ограничениями.

## Интеграция extraction fix

Если правила БВА не извлекли ни одного unit во всём загруженном корпусе, pipeline использует `semantic-pipeline.ts`: явные заголовки подразделений, буквенные списки и должностные заголовки. Сохраняются проверенные synthetic matching/lineage; результат дополнен обязательными `kind`, `category`, `clauseId` контракта v0.2.0. Clauses, alignment и проверки документов выполняются и в этом режиме. Для БВА сохранён `regulation.ts` из main. Смешанный корпус БВА и иных шаблонов не получает дополнительного fallback для отдельных документов; полнота такого анализа не гарантируется.

Оба вида evidence проверяются по исходному реестру: сырой fragmentId или fragmentId пункта; проверяются сторона, имя документа, текст, цитата и locator. Текущие интеграционные результаты — [MERGE_VALIDATION.md](runtime/MERGE_VALIDATION.md); прежние runtime-отчёты и JSON относятся к исторической ветке до интеграции.

## Правила сопоставления на контрольной паре (ред. 8 → 9)

Ожидания зафиксированы в [tests/fixtures/samples/expected-findings.json](../tests/fixtures/samples/expected-findings.json); проверка — `npm run eval` и `eval/evaluate.test.ts`. Номера пунктов в правилах не используются.

| Правило | Зачем |
| --- | --- |
| Lineage группирует несколько пунктов ДО, сведённых в один пункт ПОСЛЕ | Схема разрешает функцию только в одной записи lineage, поэтому «первый занял — остальные потеряны» давало ложные потери при похожести 0.88–1.00 |
| Пара, установленная alignment, не вытесняется похожестью | Дословная пара владельца остаётся `UNCHANGED`, даже если тот же текст есть у другого владельца |
| При отсутствии свободного кандидата предпочитается пункт под групповым заголовком | Консолидированные обязанности размещаются в групповом блоке, а не в личном блоке другого владельца |
| Совпадение по вложенности: формулировка, почти полностью содержащаяся в другой | Сужение или расширение обязанности — `SCOPE_CHANGE`, а не потеря; по токенам такая пара набирает мало |
| При равной похожести предпочитается кандидат, сохраняющий маркеры области (БВА, ДНМ, СВК) | Замена области меняет, кого и что покрывает обязанность |
| Должности сопоставляются внутри сопоставленного родителя по сохранённой основе названия | «Директор проектов ДНМ» и «Директор проектов» в составе ДНМ — одна должность, а не удаление плюс создание |
| `LOSS` публикуется с проверенной цитатой ДО и историей поиска | `verified` означает проверенную текстовую основу и исчерпанный поиск, а не доказанное исчезновение обязанности; решение остаётся за сотрудником |
| `REORGANIZATION` — одна находка на подразделение или должность | Список отвечает на вопрос «какие подразделения реорганизованы» |
| `AMBIGUITY` — одна находка на групповой заголовок | Неоднозначна область заголовка, а не каждый перенесённый пункт |
| Двойное подчинение одной должности — `CONFLICT` c `confidence=low` | По прямому требованию продукта; источник различает функциональное и административное подчинение, поэтому это кандидат для проверки, не доказанный конфликт интересов. Прежняя формулировка правила (`AMBIGUITY`) осталась в `docs/plan/PLAN.md` и требует согласования |
